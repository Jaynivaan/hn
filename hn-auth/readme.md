-----------------------------------------------------------------------------------------------------

1. Presence (VAYU) — The Breath of Awareness

Every journey begins in Vayu.

POST /challenge/issue   → {nonce, difficulty}

3. Auth (VARUNA) — The Binder of Truth

When the X-Proof token reaches Varuna, it is validated by looping back to Indra via a secure localhost request (/protected/ping).
If valid, Varuna allows the registration of a device_pub key associated with the presence_id.
This moment is the binding of awareness and authenticity — the creation of trust without data ownership.

POST /auth/register_key
Headers: X-Proof
Body: {presence_id, device_pub}
→ Returns: {auth_id, registered_at}

4. Varuna Ticket — Truth Manifest

Upon successful login (/auth/begin → /auth/complete), Varuna issues a cryptographically signed ticket using Ed25519.
This ticket is short-lived and self-verifiable, serving as proof of truth without any central lookup.

POST /auth/begin       → {nonce, exp}
POST /auth/complete    → {varuna_ticket, exp}
GET  /auth/me          → verifies DPoP-lite + ticket validity

____________________________________________________________________________________________________

5. DPoP-Lite (Proof of Possession)

Every request protected by Varuna can optionally require two headers:

X-Req-Ts: <unix_timestamp>
X-Req-Signature: <ed25519 signature of METHOD\nPATH\nTS>


This ensures the actor still possesses the key that originally registered with their presence, providing replay resistance and temporal authenticity — truth bound in motion.

🛡️ Section 8 — Security Notes
Purity of Flow, Not Possession of Data

In most systems, security means control.
In Varuna, security means alignment with truth — defense through verification, not through hoarding of data.

The hn-auth-chamber is architected to achieve full zero-PII trust, stateless verification, and tamper-proof accountability, while keeping the essence of Rta — the law of harmony — at its core.

🔐 1. PII-Free Architecture

Traditional auth systems store user credentials, metadata, and personal details.
Varuna abolishes this completely.

Element	Traditional Systems	Varuna
Identity	Username, Email, UUID	presence_id (hash of alias + salt)
Credential	Password or OAuth token	Ed25519 keypair (client-side only)
State	Server session tables	Stateless tickets (self-verifiable)
Data Ownership	Server owns user data	No data collected or persisted
Trust Basis	Administrative control	Cryptographic truth

No user information is retained, transmitted, or reconstructible — truth without trace.

🔱 2. Cryptographic Foundation

Varuna relies solely on modern asymmetric cryptography — Ed25519 (EdDSA) for all signing operations.

Purpose	Algorithm	Scope
Device Registration	Ed25519 Public Key (32 bytes)	Client-generated
Ticket Signing	Ed25519 Signature (64 bytes)	Server-signed
DPoP Validation	Ed25519 Signature	Client-signed per request

All base64 conversions use URL_SAFE encoding with no padding, making the system compatible with web transmission while preserving signature purity.

Every signature is deterministic, every ticket self-verifiable.

🧾 3. Ticket Lifecycle

The Varuna Ticket is the sacred seal of authentication — short-lived, self-contained, and unforgeable.

Phase	Description	Technical Action
Issue	On successful /auth/complete	Ed25519-signs JSON payload {sub, iat, exp, kid}
Verify	On any protected endpoint	Signature verified against public key; TTL enforced
Expire	After VARUNA_TTL_SECS (default 900s)	Ticket invalidated automatically (no revocation list needed)

No session tables, no revocation endpoints, no persistence.
When truth expires, it simply dissolves — impermanence as integrity.

🧩 4. DPoP-Lite Integrity Layer

DPoP (Proof of Possession) ensures the bearer of a ticket still controls the original private key.
Varuna’s simplified DPoP-lite approach minimizes complexity while ensuring replay resistance.

Header	Function
X-Req-Ts	Unix timestamp of request — freshness check (±60s)
X-Req-Signature	Signature over "METHOD\nPATH\nTS" using device private key

Verified in /auth/me.
If REQUIRE_POP=true, any request missing these headers is rejected.

Why it matters: Even if a ticket is intercepted, it cannot be reused — without the device’s private key, truth cannot be impersonated.

🧱 5. Defense-in-Depth (Layered Security)

Port Isolation — Each chamber runs on a separate port. Gateway (Agni) isolates public exposure.

Header Integrity — Gateway preserves cryptographic headers without modification.

No Shared Secrets — Varuna verifies tokens via Indra’s public API, never storing Indra’s secrets.

No Database Attack Surface — In-memory registries only; no persistence layer exposed.

TLS Enforcement (future) — Gateway-level HTTPS ensures all external routes are encrypted.

Result:
Even if one chamber is compromised, others remain pure — no shared secrets, no central weakness.

🌊 6. Ephemeral Truth: Memory-Only State

Varuna keeps runtime data purely in RAM:

pub type Registry = RwLock<HashMap<String, String>>;
